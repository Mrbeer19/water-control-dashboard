# DECISIONS.md — ข้อที่ backend ตัดสินเอง พร้อมเหตุผล

เรียงตามเวลา ข้อไหนถูกกลับคำตัดสินให้ขีดฆ่าแล้วเขียนข้อใหม่ ห้ามลบ

| # | เรื่อง | ตัดสินว่า | เหตุผล |
|---|---|---|---|
| D-01 | ชนิดของ id | ใช้ `TEXT` ชุดเดียวกับหน้าบ้าน (`zone-1`, `pump-1`) รวมถึง `zones.zone_id` ที่สเปกเขียนเป็น `SERIAL` | `lib/types.ts` ใช้ id เป็น string และ `lib/services/` ส่ง id นี้มาตรง ๆ ถ้าใช้ตัวเลขต้องมีตารางแปลงสองทางทุก endpoint |
| D-02 | ถังทรงเรขาคณิต (ถัง 1, ถัง VIP) | ใส่ `tank_profiles` 2 จุด (ว่าง, เต็ม) | ให้ทุกถังแปลงผ่าน `tank_volume()` ทางเดียว ไม่มีสูตร `level × area` แอบอยู่ในโค้ด · ถ้าวัดถังจริงแล้วไม่ตรงก็แค่เพิ่มจุดในตาราง |
| D-03 | index `(entity_id, time DESC)` ของ hypertable | ไม่สร้าง | PK `(entity_id, time)` เป็น btree ที่ scan ย้อนทางได้อยู่แล้ว สร้างซ้ำแค่เปลืองดิสก์และเขียนช้าลง |
| D-04 | การปัก image | ปักด้วย digest อย่างเดียว ไม่เขียน tag คู่ | ข้อห้ามเรื่อง tag `latest` · digest ชี้ของชิ้นเดียวแน่นอน ส่วนเวอร์ชันเขียนเป็นคอมเมนต์ |
| D-05 | entity ที่ไม่ได้อยู่ในรายการ 28 stream | เพิ่ม entity ของ โซน · วาล์ว · อุปกรณ์ · ระบบแรงดัน · `plant` | `alerts` / `state_spans` / `device_status` / `thresholds` มี FK ไป `entities` · 28 คือจำนวน **stream** ไม่ใช่จำนวน entity |
| D-06 | การแก้ schema | แก้ในไฟล์ `db/0x_*.sql` ได้ตรง ๆ **จนกว่าจะ deploy ครั้งแรก** | ยังไม่มีข้อมูลจริงที่ต้องย้าย · หลัง deploy แล้วต้องเพิ่มไฟล์ migration ใหม่เท่านั้น |
| D-07 | ACL ของ MQTT | ไฟล์ `mosquitto/acl` เขียนตรง ๆ ต่ออุปกรณ์ ตรงกับ seed | อุปกรณ์ส่งใน topic ของ entity (`tank/tank-1`) ไม่ใช่ของตัวเอง จึงใช้ `pattern %u` ไม่ได้ · เพิ่มอุปกรณ์ต้องแก้ acl + seed + รัน `gen_passwd.sh` |
| D-08 | branch | ทำใน `feature/pitchakorn-backend` branch เดียว commit แยกตามเฟส | เจ้าของงานขอ branch backend ก้อนเดียวไว้ push ขึ้น repo ทีม · ถ้าทีมอยากได้ PR ย่อยตาม `REPO_INTEGRATION.md` แตกจาก commit ของแต่ละเฟสได้ภายหลัง |
| D-09 | `rain_mm` ใน payload | ถือเป็น **ปริมาณต่อรอบส่ง** (`kind: amount`) | ตรงกับ `metric → kind` ใน HANDOFF §2.11 · ⚠️ ยังต้องยืนยันกับทีมฮาร์ดแวร์ (PROMPT_03) ถ้าเป็นค่าสะสมต้องเปลี่ยนเป็นคิดแบบ counter ภายใน |
| D-10 | `device_id` ของปั๊ม | ชี้ ESP32 ที่ **วัด** ค่า (PZEM) ส่วน PLC ที่ **สั่ง** เก็บใน `spec.controlledBy` | ตรงกับ `PumpSpec.deviceId` ในหน้าบ้าน · node วัดตาย = ปั๊ม offline ในมุมมองข้อมูล แม้ PLC ยังสั่งได้ |
| D-11 | ฟังก์ชันค่าน้ำ | `water_cost(m3, config)` คำนวณล้วน · `water_cost_at(m3, date)` เลือกอัตราตาม `effective_from` · `water_cost(m3)` = อัตราวันนี้ | แยกการคำนวณออกจากการเลือกอัตรา ทดสอบขั้นบันไดได้โดยไม่แตะตาราง และรายงานย้อนหลังเรียกด้วยวันที่ของข้อมูล |
| D-12 | ขอบขั้นบันได | ขั้นต่อเนื่อง `0–30, 30–50, …` (ไม่ใช่ `31–50`) | ตรงกับ `billing.tiers` ใน `lib/mock/settings.ts` · ปริมาณเป็นทศนิยม ช่วงเว้น 30–31 จะทำให้ 30.5 m³ ไม่อยู่ขั้นไหนเลย |
| D-13 | ชื่อ field ใน payload | กำหนดสัญญาใน `README.md` หัวข้อ "สัญญา payload" (`levelMeters`, `currentAmp`, `energyKwh`, `phases.L1` …) | PROJECT_BRIEF §7.1 ให้ตัวอย่างแค่ถัง · ⚠️ **ต้องให้ทีมฮาร์ดแวร์ยืนยัน** ถ้าเปลี่ยนชื่อ แก้ที่ `ingest/normalize.py` ที่เดียว และ ingest log `unknown_field` ให้เห็นทันทีเมื่อชื่อไม่ตรง |
| D-14 | `at` ที่ไม่มี offset | ทิ้งทั้งข้อความ + log `at_without_offset` | ไม่รู้ว่าเป็นเวลาเขตไหน เก็บไปก็ไปโผล่ผิดที่บนกราฟ 7 ชั่วโมง · ต่างจาก `clock_skew` ที่ offset ถูกแต่นาฬิกาเพี้ยน ซึ่ง**ยังเก็บ** |

| D-17 | อุปกรณ์ที่เฝ้า offline | เฝ้า ESP32 ทุกตัวตั้งแต่เริ่ม · PLC/HMI/gateway เฝ้าเมื่อเคยส่งข้อความมาแล้ว | PLC/HMI ไม่ได้ส่ง MQTT เอง ถ้าเฝ้าตั้งแต่ต้นจะมี `DEVICE_OFFLINE` ค้างตลอด |
